1. Introduction

1.1 Purpose

The purpose of this Software Requirements Specification (SRS) document is to provide a complete, rigorous, and verifiable specification for the Outage Management and Restoration System (OMRS) (Project Code: J16, Domain: Energy & Utilities). This document serves as the formal design and evaluation baseline for the 2nd-year Master of Computer Applications (MCA) capstone project at ABES Engineering College, Ghaziabad (Affiliated to Dr. A.P.J. Abdul Kalam Technical University, Lucknow).

1.2 Scope of the System

Power distribution utilities consistently suffer from prolonged restoration delays, consumer frustration, and operational opacity due to manual phone logging of faults, lack of coordination between control room dispatchers and field crews, and zero real-time progress visibility.

The OMRS platform automates this end-to-end lifecycle within a unified, modern web monorepo:

  • In-Scope Capabilities: Centralized incident reporting for consumers and operators; automated duplicate incident clustering by areaId and feederId; role-based access control across 4 distinct user tiers; conflict-free crew scheduling and work order dispatching; granular progress tracking (0% to 100%) with dynamic ETR adjustments; multi-channel notification simulation stored directly in database logs; and real-time analytical KPI dashboard visualization.
  • Out-of-Scope Boundaries: Physical hardware sensor fabrication (SCADA/AMI telemetry is abstracted via simulated REST events); paid third-party commercial SMS/Email telecom gateways (simulated in mock sandbox mode and written to Oracle database tables); and real-time GPS telemetry hardware.
  • Measurable Objectives: Reduce mean time to dispatch (MTTD) by 55%, eliminate redundant crew dispatches to identical feeder faults, and provide 100% transparent milestone updates to affected consumers.

2. Overall Description

2.1 Product Perspective & Multi-Tier Architecture

The system is implemented as a cloud-ready, 3-tier enterprise architecture structured within a clean monorepo:

  • Presentation Layer: Angular 17+ standalone architecture utilizing Angular Router, Reactive Forms, functional interceptors (jwtInterceptor, errorInterceptor), and functional route guards (authGuard, roleGuard).
  • Application Layer: Java 17 + Spring Boot 3.2.4 REST services organized into layered packages: controller, service, repository, entity, dto, config, security, and exception.
  • Database Layer: Oracle Database 21c XE on port 1521 (XEPDB1) accessed via the ojdbc11 driver, enforcing 3NF relational normalization and sequence-backed identity primary keys.

2.3 User Classes and Characteristics

User Role / Persona Technical Level Responsibilities & Access Rights
Control Room Operator / Admin (ROLE_ADMIN) High Complete operational access: verifies outage reports, manages crews, dispatches work orders, broadcasts area emergency alerts, and monitors real-time KPI dashboards.
Field Engineer (ROLE_FIELD_ENGINEER) Intermediate Views assigned work orders, logs restoration milestones (0% to 100%), updates technical remarks, revises ETR, and auto-closes incidents.
Customer / Consumer (ROLE_CUSTOMER) Basic Reports localized outages with area/feeder details, tracks real-time restoration progress, and views personalized notification alert feeds.
Crew Member (ROLE_CREW_MEMBER) Basic View-only access to assigned work orders, vehicle assignments, and site location remarks.

2.4 Operating Environment

  • Client Environment: Modern standards-compliant browser (Google Chrome ≥ 110, Microsoft Edge ≥ 110, Mozilla Firefox ≥ 108); desktop ≥ 1366×768, responsive mobile down to 360×640.
  • Server Environment: Java 17 LTS, Spring Boot 3.2.4, Apache Maven 3.9+, Node.js v18+ / npm v10+.
  • Database Tier: Oracle Database 21c Express Edition (XE); Service: XEPDB1; Port: 1521.

2.5 Design and Implementation Constraints

  1. Architectural Separation: Strict MVC + DTO architecture. JPA Entities are never exposed over REST endpoints directly.
  2. Cryptographic Security: Passwords stored exclusively as salted BCrypt hashes (strength 10). Stateless authentication enforced via signed JJWT tokens (HS256).
  3. Relational Normalization: Database schema strictly normalized to Third Normal Form (3NF) to eliminate data redundancy.
  4. Dispatch Safety: The dispatch engine must strictly reject assigning any crew marked DISPATCHED or ON_DUTY to an active work order.

3. System Features & Functional Requirements

3.1 Module 1: Authentication & Role-Based Access Governance

Req ID Feature Processing Logic & Validation Rules REST Endpoint
FR-1.1 User Registration Validates unique username, RFC email format, and password (≥ 6 characters). Assigns default ROLE_CUSTOMER. POST /api/auth/register
FR-1.2 Secure JWT Login Authenticates credentials against BCrypt hash; generates signed HS256 JWT bearer token containing user ID, username, and roles. POST /api/auth/login
FR-1.3 Token Management Token lifetime set to 7,200 seconds (120 minutes). Expired or tampered tokens return 401 Unauthorized. Header: Bearer <token>
FR-1.4 Role Route Guards Angular functional guards (authGuard, roleGuard) protect client views according to JWT role claims. Client Router

3.2 Module 2: Outage Detection, Reporting & Duplicate Grouping

Req ID Feature Processing Logic & Validation Rules REST Endpoint
FR-2.1 Report New Outage Requires areaId, feederId, severity (LOW, MEDIUM, HIGH, CRITICAL), and description. Generates OUT-YYYY-XXXX code. POST /api/outages/report
FR-2.2 Duplicate Grouping Checks active incidents for the same area and feeder. If found, groups incoming report under the active incident and increments report_count. System Automatic Logic
FR-2.3 Outage Verification Control Room Operator verifies incident; advances status from REPORTED → VERIFIED. PUT /api/outages/{id}/verify
FR-2.4 Search & Filter Multi-parameter filtering by area, feeder, status, and severity with server-side pagination. GET /api/outages
FR-2.5 Status Lifecycle Enforces valid state machine: REPORTED → VERIFIED → IN_PROGRESS → RESTORED. PUT /api/outages/{id}/status

3.3 Module 3: Crew Dispatch & Work Order Management

Req ID Feature Processing Logic & Validation Rules REST Endpoint
FR-3.1 Crew Inventory CRUD Manages repair crews (crew name, code, vehicle number, team members count, base area ID). POST /api/crews
GET /api/crews
FR-3.2 Query Available Crews Filters crews whose status is AVAILABLE. Excludes DISPATCHED or ON_DUTY crews. GET /api/crews/available
FR-3.3 Work Order Creation Creates a work order (WO-YYYY-XXXX) linked to a verified outage with assigned priority and target duration. POST /api/work-orders
FR-3.4 Crew Dispatch Logic Assigns available crew to work order. Sets WO status to ASSIGNED and flips crew status to DISPATCHED. Throws BadRequestException if crew is busy. POST /api/work-orders/{id}/assign
FR-3.5 Work Order Lifecycle Enforces status progression: CREATED → ASSIGNED → EN_ROUTE → WORKING → COMPLETED. PUT /api/work-orders/{id}/status

3.4 Module 4: Restoration Progress Tracking & Auto-Closure

Req ID Feature Processing Logic & Validation Rules REST Endpoint
FR-4.1 Log Milestone Update Field Engineer submits milestone percentage (0–100%), technical remarks, and status reached. POST /api/restoration/updates
FR-4.2 Chronological Timeline Fetches ordered history of all milestone updates recorded for an outage incident. GET /api/restoration/outage/{id}/timeline
FR-4.3 Dynamic ETR Update Revising the Estimated Time of Restoration automatically triggers notifications to affected consumers. PUT /api/restoration/outage/{id}/etr
FR-4.4 Automated Closure Upon 100% completion & WO marked COMPLETED: 1) Outage status becomes RESTORED; 2) actual_restore_time set; 3) duration calculated; 4) assigned crew reset to AVAILABLE. Automatic upon 100% Milestone

3.5 Module 5: Customer Notification & Communication

Req ID Feature Processing Logic & Validation Rules REST Endpoint
FR-5.1 Template Engine Replaces placeholders ({outageNumber}, {areaName}, {etr}) from templates on status changes. System Automatic Logic
FR-5.2 Alert Persistence Stores alert records in the NOTIFICATIONS table with channels (SMS, EMAIL, IN_APP) and status SENT. Database Persistence
FR-5.3 Customer Alert Feed Consumers view historical alerts mapped to their user account and registered meters. GET /api/notifications/my
FR-5.4 Area Broadcast Operator broadcasts emergency notices to all consumers mapped to a target areaId. POST /api/notifications/broadcast

3.6 Module 6: Control Room Analytics & OpenAPI Documentation

Req ID Feature Processing Logic & Validation Rules REST Endpoint
FR-6.1 Live KPI Metrics Returns live aggregate counts: Active Outages, Available Crews, Restored Today, and Pending Alerts. GET /api/dashboard/stats
FR-6.2 Area Feeder Lookups Supplies reference dropdown data for areas, substations, and feeders. GET /api/lookup/areas
GET /api/lookup/feeders
FR-6.3 Interactive Swagger Full OpenAPI 3.0 interactive test explorer rendered via SpringDoc. /swagger-ui.html

4.2 Hardware Interfaces

Standard I/O peripherals (Keyboard, Mouse, Display ≥ 720p). Mobile and tablet devices for Field Engineers supported through responsive browser viewports down to 360×640. No embedded microcontroller hardware is required for this software baseline.

4.3 Software Interfaces

  • Database Connector: Spring Data JPA / Hibernate 6 over JDBC Type-4 driver (ojdbc11) connecting to Oracle Database 21c XE on port 1521 (jdbc:oracle:thin:@localhost:1521/XEPDB1).
  • Security Provider: Spring Security 6.2 and JJWT (version 0.12.5) implementing HMAC-SHA256 signature verification.
  • Documentation: SpringDoc OpenAPI Starter WebMVC UI (version 2.4.0) hosting Swagger endpoints at /swagger-ui.html.

4.4 Communications Interfaces

  • Network Protocol: HTTP/1.1 and HTTPS (TLS 1.3).
  • Data Interchange: All payloads serialized strictly as UTF-8 encoded application/json.
  • CORS Policy: Configured to explicitly permit origins from http://localhost:4200 with HTTP verbs GET, POST, PUT, DELETE, OPTIONS.

5. Non-Functional Requirements (NFRs)

NFR Category Target Metric / Standard Implementation & Verification Method
5.1 Performance Page load latency < 2.0s; API response time < 300ms under 50 concurrent requests. Connection pooling via HikariCP, composite B-tree indexes on Oracle tables (area_id, feeder_id, status).
5.2 Security Zero plain-text passwords; stateless token-based authorization; OWASP SQL injection immunity. BCrypt password hashing (strength 10), JJWT HS256 filter, Spring Data JPA parameterized queries.
5.3 Reliability System availability ≥ 99.5%; transactional integrity during multi-table updates. @Transactional boundaries on all service updates; standard JSON error format via @ControllerAdvice.
5.4 Maintainability Layered modular design; cross-browser portability. Strict separation of controller, service, repository, and DTO layers; Angular responsive flexbox design.

    else New Outage Incident
        Backend->>DB: INSERT into OUTAGES (status='REPORTED')
        Backend->>DB: INSERT notification log
        Backend-->>Angular: 201 Created (New OUT-2026-YYYY)
    end

    Operator->>Angular: Review Incident & Click "Verify Outage"
    Angular->>Backend: PUT /api/outages/{id}/verify
    Backend->>DB: UPDATE OUTAGES SET status='VERIFIED'
    Backend-->>Angular: 200 OK

    Operator->>Angular: Select Available Crew & Assign Work Order
    Angular->>Backend: POST /api/work-orders/{id}/assign (crewId=3)
    Backend->>DB: Verify Crew 3 status == 'AVAILABLE'
    Backend->>DB: INSERT WORK_ORDERS & UPDATE CREWS SET availability='DISPATCHED'
    Backend->>DB: Trigger Notification ("Crew Dispatched")
    Backend-->>Angular: 200 OK (Work Order ASSIGNED)

    Engineer->>Angular: Log Milestone Progress (40%, Remarks)
    Angular->>Backend: POST /api/restoration/updates
    Backend->>DB: INSERT PROGRESS_UPDATES (percentage=40)
    Backend-->>Angular: 200 OK

    Engineer->>Angular: Log Final Milestone (100%, Status='COMPLETED')
    Angular->>Backend: POST /api/restoration/updates (percentage=100)
    Backend->>DB: INSERT PROGRESS_UPDATES
    Backend->>DB: UPDATE WORK_ORDERS SET status='COMPLETED'
    Backend->>DB: UPDATE OUTAGES SET status='RESTORED', actual_restore_time=CURRENT_TIMESTAMP
    Backend->>DB: UPDATE CREWS SET availability='AVAILABLE'
    Backend->>DB: Trigger Notification ("Power Restored")
    Backend-->>Angular: 200 OK (Incident Auto-Closed)
    Backend-->>Customer: Real-Time Power Restored Alert
